# REVIEW.md

This review records the defects identified in the starter implementation, how to reproduce or detect them, and the corresponding corrections made in the submitted implementation.

## Defects found and fixed

| # | Location | Problem | How to detect it | Fix |
|---|---|---|---|---|
| 1 | `PunchInRequest.punched_at`, `PunchOutRequest.punched_at`, `RegularizeRequest.punch_in/punch_out`; `validate_epoch()` | Pydantic's normal integer parsing can coerce a numeric string such as `"1791800000000"` into an integer before the validator runs. The API can therefore accept a string even though the contract requires an integer epoch-millisecond value. | Send a numeric string, a float, and a boolean as a timestamp. Each must return `422`. | Validate the raw input before coercion (or use strict integer types), then apply the epoch-millisecond range check. |
| 2 | `shift_datetimes()` | For an overnight shift, the date adjustment used `< end_min`. A punch exactly at the shift-end clock time was assigned to the current calendar date instead of the previous shift date. | For a `22:00–06:00` shift, test a punch at exactly `06:00` local time and check the attendance date. | Treat the end-time boundary consistently as belonging to the overnight shift that started the previous day. |
| 3 | `punch_out()` attendance lookup | The query selected the latest presence record without requiring `punch_out` to be open (`None`). A newer closed record could be selected even when an earlier eligible open record existed. | Create a closed attendance record and an earlier open record for the same employee, then punch out. | Select an eligible open record explicitly and use a separate lookup to distinguish an already-closed record from a missing punch-in. |
| 4 | `punch_out()` time validation | The time-order check happened only after record selection, so an earlier requested punch-out could be reported as `404` when the query filtered or selected the wrong record rather than returning a validation error. | Punch in at `09:30` and submit a punch-out at `09:29` on the same shift. | Ensure the correct record is located first, then return `422` when punch-out is not after punch-in. |
| 5 | `regularize_attendance()` compare-and-swap filter | The concurrency filter compared `history` to `original.get("history", [])`. If the field was absent in an older/seeded record, querying for an exact empty array did not match the missing field, producing a false conflict. | Remove `history` from a test record and perform a valid regularization. | Build a compare-and-swap condition that handles both a missing history field and an empty history array, while retaining the other version checks. |
| 6 | `regularize_attendance()` history update | Concurrent updates can overwrite each other's audit history if the operation is implemented as a read-modify-write without an atomic condition. | Send two regularization requests concurrently and inspect the final history. | Use an atomic conditional update and `$push` for the history entry; return `409` when the record has changed since it was read. |
| 7 | `regularize_attendance()` no-op handling | A request containing only audit metadata must not create a history entry when it changes no attendance fields. This needs to be checked against the full final record, including derived values. | PATCH a record with only `reason` and `regularized_by`, leaving all attendance values unchanged. | Compare the proposed final values with stored values and return `422` when there are no actual changes. |
| 8 | `record_out()` nested history conversion | A shallow copy of the record still shares nested history dictionaries with the original object. Converting timestamps in those nested dictionaries mutates the input object in place. | Call the serializer with a record containing history and inspect the original dictionary afterward. | Copy nested history/change structures before converting stored datetimes to API epoch milliseconds. |
| 9 | `explain_execution("employee_monthly", ...)` | The explain pipeline was only a simplified grouping query, not the main pipeline used by the monthly analytics endpoint. Its plan did not prove the actual endpoint's query shape. | Compare the endpoint's aggregation pipeline with the pipeline passed to `explain`. | Build explain input from the same match, grouping, and calculation stages used by the actual endpoint. |
| 10 | `explain_execution("department_summary", ...)` | The explain pipeline used a simplified `$lookup` by employee code and omitted the reporting-month filters and the rest of the summary pipeline. | Compare the explain pipeline with the department-summary endpoint for a month containing records outside that month. | Explain the actual department-summary pipeline with the same date range, optional department filter, and aggregation stages. |
| 11 | `explain_execution("late_leaderboard", ...)` | The explain pipeline omitted the optional department filter, employee lookup fields, ranking, tie handling, and rank-based limit used by the real leaderboard. | Request an explain with a department filter and compare the pipeline to the leaderboard endpoint. | Use the actual leaderboard pipeline, including its lookup, rank window, tie-preserving limit, and deterministic ordering. |
| 12 | `explain_execution("department_trend", ...)` | The explain branch explained a `find` query rather than the database-level aggregation that builds the date spine, fills missing dates, calculates headcount, and computes the moving average. | Compare the explain command with the trend endpoint's `$documents`, `$lookup`, and window stages. | Explain the actual trend aggregation pipeline with the same department and date range parameters. |
| 13 | `department_summary()` average-hours calculation | MongoDB `$round` uses half-even rounding, which can differ from the assignment's required half-up rounding at exact ties. | Use an average with a tie such as `1.125` and compare the result with half-up rounding to two decimals. | Use an aggregation expression implementing half-up rounding for reported numeric values. |
| 14 | `department_trend()` attendance-rate and moving-average calculations | `$round` can apply half-even rounding to rate values, conflicting with the required half-up rule for reported rates. | Construct a rate or moving average at an exact four-decimal tie. | Apply half-up rounding to both attendance rates and moving averages. |
| 15 | `department_trend()` employee-code lookup | The pipeline construction called `employees.distinct("emp_code", ...)` and then fetched the same distinct codes again before execution. This performs redundant database work for each request. | Trace database calls for one trend request. | Fetch the department's employee codes once and reuse that result when building the aggregation. |
| 16 | `StrictModel` | `extra="ignore"` silently discards unknown request fields. A client can send unsupported or server-derived fields without being told that the request contains invalid data. | Send an unexpected field such as `work_hours` in a punch-in request and observe whether it is silently ignored. | Reject extra request fields where strict request validation is required, so clients cannot mistake ignored fields for accepted input. |

## Items reviewed and considered acceptable

- `load_dotenv()` is called without `override=True`, so environment variables take precedence over values in `.env`.
- The unique indexes on `employees.emp_code` and `attendance_logs (emp_code, date)` are appropriate for identity and duplicate-day protection; duplicate-key errors are mapped to `409` on employee creation and punch-in.
- `validate_epoch()` rejects booleans and non-integer values when they reach the validator, and checks a plausible epoch-millisecond range. The request model must preserve the raw type so Pydantic cannot coerce strings first.
- `parse_date()` checks round-trip ISO formatting, and `month_bounds()` validates the `YYYY-MM` shape and derives the calendar-month boundaries.
- The punch-in grace-period check correctly treats exactly 10 minutes as not late and uses whole elapsed minutes after the grace period.
- Overtime is counted only when the elapsed time after shift end is at least 30 minutes; reported work hours are rounded to two decimal places before the half-day threshold is applied.
- Employee and attendance list endpoints use bounded pagination and calculate `total` from the same filter used for the result set.
- Analytics should remain aggregation-based and be verified against the hidden-scale requirement with explain plans; passing small integration tests alone does not prove the absence of `COLLSCAN` on the 100,000-record dataset.

## Verification note

The integration suite exercises validation, attendance rules, concurrency, regularization, analytics, and explain responses. Results should be recorded only after running the suite against the configured test MongoDB database. The explain endpoint must also be checked on the assignment-sized dataset to confirm the expected index scans and absence of collection scans.
